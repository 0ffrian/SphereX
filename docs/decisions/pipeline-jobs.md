| Q-111 | **Two-stage answer, object jobs and progress endpoints (issue #41; D-16, D-25, D-32, Q-39).** (1) **One background job per object** (`backend/app/core/jobs.py`, `ObjectPipeline` in `app/core/card/service.py`). After Find it starts the catalogue (SIMBAD or SBDB, Exoplanet Archive, shape-model registry), the Horizons geometry and the frame list together; catalogue and geometry join at the card. Repeat requests join the running job; a finished job is reused for `SX_JOB_TTL_S` (600 s); a failed job is not reused. This replaces the per-object lock and recent-results memo on `feat/sculptor-page`. (2) **Answers in up to three steps.** **First stage:** the job's first batch downloads at most `SX_LIVE_CUTOUTS_PER_REQUEST` cutouts (the frames the old per-request cap took, in time order); if that batch is not done when the card can be built and the backend is online, the job publishes a card and render params from catalogue data. Card fields the spectrum fills are not guessed: `spherex_rgb` and `flux_45um` are `value: null` with `source` starting `measuring:`, and `lightcurve` (a plain list in R3.2, with no `source`) is empty; `X-SX-Measuring` and the params entries below say why; `RenderParams.missing` lists `measuring:spectrum` and `measuring:<layer>` for each refused layer or haptic source that needs one of them (instead of `spectrum` and `<layer>`; for example `measuring:heartbeat` and `measuring:dimming` for a Mira or T Tauri star's light curve). A layer that can answer from a lower tier (D-32) still does. **Partial:** if frames remain after the first batch, a card and render params measured from that batch go out with `measuring:frames` in `RenderParams.missing`, and the rest download (Barnard's Star has 240 frames, so the complete spectrum takes minutes at a polite concurrency). **Final:** the complete frame list; saved when its inputs are final, as before. Intermediate answers are never guessed and never saved. `/card` and `/render-params` return the final answer if it comes within `SX_FIRST_ANSWER_WAIT_S` (2 s), else the newest intermediate one. Offline (D-25) nothing downloads, so there is no intermediate answer. With no intermediate answer yet (offline, or a first batch that finished before the card was built), `/card` waits for the final one with no time limit of its own. If the rest of the frames cannot be fetched, the last answer keeps `measuring:frames` and is not saved. (3) **Headers (extends Q-39):** a reply that still has `measuring:` items carries `X-SX-Measuring` (those items, comma-separated) and `X-SX-Progress` (`frames <done>/<total>` of all SIA rows, `?` before the search answers). That is every intermediate reply, and also a final reply built from the first batch only because the rest could not be fetched (it keeps `measuring:frames`); a complete final reply carries neither. CORS exposes both. (4) **Endpoints beyond D-16:** `GET /v1/objects/{id}/job` returns `{id, state: running\|done\|failed, stage: queued\|catalogue\|frames\|spectrum\|card\|done, frames_done, frames_total, answer: none\|first\|partial\|final, started_at, finished_at, error, seq}`, or `{id, state: idle}` when there is no job (it never starts one). `GET /v1/objects/{id}/job/events` streams the same JSON as server-sent events, one per change, until the job ends. (5) **`/frames`, `/spectrum` and the overlays no longer download cutouts in the request:** a capped request starts or joins the job and lists the cutouts still to come as `cutouts:deferred:<n>`, so the Q-97 client loop gets a fast reply each time and sees progress. Proposal: add the two endpoints to D-16; the frontend build steps read `/job/events`. (6) **Reading of #41's targets:** "body within about 15 s" is the first-stage answer (13.1 s cold for Barnard's Star, 11.1 s of it the SIMBAD resolve); "refined card within about 90 s" is the partial answer from the first 24 frames (70 s). The complete 240-frame answer took 458 s, limited by IRSA at about 20 s per cutout. The issue's Teff branch is not in this change (it is on `feat/sculptor-page`). The `/job` payload is the `JobStatus` model in `backend/app/api/models.py` (shown in OpenAPI); a `shared/schemas/` schema (D-18) is to add when the frontend reads it. (7) **Owners (proposal):** `app/core/jobs.py` and `app/core/warm.py` are pipeline orchestration for the API, so Kevin (D-17); `app/core/measure/pool.py` stays with stage 2 (Moon), `app/core/render/background.py` with the baker (Atish). **Spec:** [A4.10](../architecture/jobs.md#a410-object-job-and-fan-out) holds the as-built rules (answers, headers, endpoints, owners, timings). | Moon, Kevin | Open (implemented as described) |
| Q-112 | **Fan-out settings and defaults (issue #41).** `SX_CUTOUT_CONCURRENCY=6`: one cutout download pool shared by every object (so the limit holds across jobs), the pre-fetch's default concurrency; **[verify]** the polite limit with IRSA (A3.1). Each frame list keeps at most that many of its own downloads in the pool at once, so objects take turns and one large object (Barnard's Star, 240 frames) cannot hold back another's first batch. A download dropped at shutdown is refused as `cutout:<id>`. `SX_MAX_JOBS=4`: object jobs downloading all their frames at once (the long part, after the first batch); the others wait in stage `queued` with their first and partial answers already out, so every visitor gets an answer quickly. The first batch is capped per job and the pool is shared fairly, so downloads stay bounded; each object id still gets one job thread (ASSUMPTION: 4 covers a demo with a few phones). Frame outcomes are kept by row and assembled in row order, and the spectrum by frame order, so the result does not depend on finishing order (tested with shuffled delays). `SX_MEASURE_WORKERS=2`: photometry in `spawn` worker processes, each frame sent the moment its cutout lands, reused only when the cutout bytes' SHA-256 and pixel position match (ASSUMPTION: 2 leaves cores for the API and the bake on the A15). `SX_BAKE_TEXTURES=1`, `SX_BAKE_WORKERS=1`: when a reply's render params point at textures, both R5 sizes (2048x1024 and 1024x512, R6.7 size directories) are baked in a worker process off the request path and served at `/data/textures` (`SX_TEXTURES_DIR`, default `<SX_CACHE_DIR>/textures`); the reply does not wait, so a texture URL can answer 404 for the first seconds. `SX_PREFETCH_ON_START=0`, `SX_PREFETCH_GROUPS=demo`: with `1`, the API runs the object job for every target of those `targets.toml` groups at start-up, one at a time (D-25 warm cache; overlays and composite stay with `scripts.prefetch`). Off by default because it reaches the network. **For the event:** run the demo laptop with `SX_PREFETCH_ON_START=1` together with `SX_OFFLINE=1`, so every demo object's card is built and its textures baked from the cache before visitors arrive (textures otherwise bake on the first view, about 17 s, during which the URL answers 404). While a job waits for an `SX_MAX_JOBS` slot (`stage: queued`) its frame count does not move; a client that gives up after replies without progress (the Q-97 loop) should read `stage` from `/job` first. Confirm the defaults. **Spec:** [A4.10](../architecture/jobs.md#a410-object-job-and-fan-out) (settings and warm start), [A10.2](../architecture/frontend-platform.md#a102-running-the-event-build) (event run). | Moon, Kevin | Open (implemented as described) |
