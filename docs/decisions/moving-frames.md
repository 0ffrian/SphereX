| Q-21 | Frames for moving objects. A moving body needs an ephemeris-driven SIA search (many tiny cones along its path over the data release window); one cone does not find it. In M1, `/v1/objects/{id}/frames` for a moving object returned `frames: []` and `missing: ["frames:moving_object_search"]`. The 3I/ATLAS demo and Rainbow Trails (D-28) depend on this search. When is it built, and how many cones can IRSA take? **Built in issue #26** (`backend/app/core/find/moving.py`, [A4.1](../architecture/pipeline.md#a41-stage-1-find-the-object)): one SPHEREx-centred Horizons ephemeris over `SX_MOVING_WINDOW_START`–`SX_MOVING_WINDOW_END`, SIA cones along the path with the step dt = clamp(R / rate, min, max) from the ephemeris rate, merged by `frame_id`, kept when the interpolated position at the frame midpoint is inside the `s_region` footprint, then exact SPHEREx-centred positions per frame midpoint (TLIST); Stage 2 measures those frames. `frames:moving_object_search` is no longer emitted. 433 Eros (fixtures recorded live 7 Nov 2026, 20–21 Mar 2026 window) gives 16 frames, their pixels and a spectrum offline. Still open: IRSA publishes no rate limit (astro-verifier, 7 Nov 2026), so the cone radius, step clamp, cone cap (`frames:truncated` past it) and pacing are configurable **[verify]** placeholders; MOST as the primary search is proposed in Q-126. **Status note (9 Nov 2026):** continued in Q-140 (PR #53 builds the cone search). The 3I/ATLAS dependency is no longer the driver: Q-137 makes 433 Eros the MVP and 3I/ATLAS a stretch. | Kevin | Partly answered (built; limits [verify], Q-126) |
| Q-125 | Tags and refusals of the moving-object frame search (issue #26, PR #53; A4.1, A4.2, R1.2). A4.1 tags `x`, `y` and the propagated `ra`/`dec` `derived`, a rule written for proper-motion stars; R1.2 defines `derived` as computed from **measured** values. A mover's position is a Horizons prediction (A3.4: `model_dependent`). Implemented: per-frame `ra`/`dec` are `model_dependent` with the assumption "JPL Horizons orbit solution; astrometric RA/Dec (ICRF) seen from the SPHEREx spacecraft (CENTER=500@-163182), TIME_TYPE=UT, at the frame midpoint", and `x`/`y` are `model_dependent` too (same pixel formula, plus that assumption), because they are computed from that position. `wavelength_um` stays `measured` (a WCS-WAVE lookup), although it is read at the predicted pixel. The spectrum keeps `tag: measured` (the photometry is measured; only the aperture centre is predicted). **Search (PR #53 review):** the path is sampled every 10 min (`SX_MOVING_EPHEM_STEP_MIN`), inside the ~95 min SPHEREx orbit; a frame is a candidate when the interpolated path is inside its `s_region` or within `SX_MOVING_FOOTPRINT_MARGIN_ARCSEC` (60″, ASSUMPTION) of its edge, and is kept only when the exact SPHEREx-centred TLIST position is inside. A target may list `moving_windows` in `targets.toml`, matched by its `spkid` so every spelling of the name gets the same windows (3I/ATLAS: its two QR2 spans); a window that fails is reported as `frames:ephemeris` while the others are still searched; past `SX_MOVING_MAX_CONES` the cones are spread evenly over the whole path. Under Q-111 a web request, and the job's capped first batch, run the search from the cache only; the job's full run downloads the rest; a call that failed live is not retried within `SX_LIVE_FAILURE_TTL_S`; `SX_MOVING_LIVE_CONES_PER_REQUEST` is retired. **`missing` codes:** whole-result `frames:ephemeris`, `frames:moving_window` (a window shorter than one ephemeris step), `frames:cone_cap:<n>` (cones left out by the cap), `frames:cone_maxrec:<n>` (cone answers that hit MAXREC; a fixed object keeps `frames:truncated`), `frames:sparse_path:<n>` (the minimum step overrode `R / rate` at `n` cones), `frames:cone_failed:<n>`, `frames:search_deferred:<n>` (calls left to the job), `frames:outside_window:<n>`; per frame `no_footprint:<frame_id>` (no usable `s_region`; distinct from the UI's `footprint:<id>`) and `ephemeris:<frame_id>`. The list is stored unless it has `frames:ephemeris`, `cone_failed`, `search_deferred` or `ephemeris:` (the cap, MAXREC and the sparse path are deterministic for the settings in the key). The exact-position TLISTs are grouped by the nearest planned cone time, so their cache keys do not depend on which cones answered. The frontend words every code (`refusals.ts` `COUNTED_CODES` and `MOVING_FRAME_REASONS`, `messages.ts`; `backendReasons.test.ts` checks every code in `moving.py` has wording), keeps polling while `frames:search_deferred` is listed (counted as progress, so the poll does not stall out), and treats the cap, MAXREC, sparse path, failed cones and a missing ephemeris as a possibly incomplete list; `frames:moving_object_search` is retired there too. Moon owns `app/` (D-17) and should confirm the wording. `ASSET_VERSION` is bumped to 6, so Eros cards saved without a spectrum are rebuilt. **Finding:** on the recorded Eros frames the pipeline sets `OUTLIER` (and `PERSIST`) at the asteroid's own pixels, so Stage 2 refuses 15 of 16 frames as `aperture_flags` (1 measured point, at 2.81 µm, flagged). The SPHEREx outlier rejection appears to flag the moving source itself **[verify against the Explanatory Supplement]**. Should Stage 2 keep `OUTLIER`/`TRANSIENT` at a mover's core (flagged, not refused), and should `x`/`y` and the spectrum tags change? Overlays for movers now list each frame's flag mask and cutout box; the catalogue cones are still refused and the footprint is refused per frame (`footprint:<id>`), because the frame record does not carry `s_region`. | Kevin, Atish, Moon | Open (implemented as described) |
| Q-126 | Use IRSA's Moving Object Search Tool (MOST) as the primary SPHEREx search for moving objects? IRSA's MOST (`https://irsa.ipac.caltech.edu/cgi-bin/MOST/nph-most`, `catalog=spherex`; program interface: https://irsa.ipac.caltech.edu/applications/MOST/MOSTProgramInterface.html) returns every frame that contains a solar-system body in one request (astro-verifier, 7 Nov 2026). It is an endpoint no spec lists, so issue #26 does not use it and builds the SIA-cone path search instead (Q-21). Proposal: MOST first, the cone path search as the fallback when MOST fails or does not cover the release, both through the D-25 cache; the Stage 1 positions would still come from the SPHEREx-centred Horizons ephemeris. Needs an A3.1 entry, a check of MOST's SPHEREx coverage for QR2/QR3 and of its answer format **[verify]**. | Kevin | Open |
