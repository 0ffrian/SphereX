> **As built (issue #96, PR #100; Q-406, 13 Nov 2026):** Area search is started from the sky dock (Known objects, Discovery; PR #104, Q-414), not a rail tool. `app/area/areaService.ts` snaps the drawn area (its centre, larger side) to `GET /v1/areas` with the gnomonic geometry of `app/sky/area/geometry.ts` and `snap.ts`, and reads that area's stored replies through `app/area/realArea.ts` (the validated client methods `areaIndex`, `area`, `areaDots`, `areaTracks`, `areaKnown`); where no prepared area holds it, the Q-414 demo answers. Not built from this fragment: the Options card, Fly there, the pointer mode and feature card (A21), the `area=` / `atrack=` hash keys, blink (A18.3; a Visit picker instead), the Result card's Track hand-off and the text alternative. Owner: Moon (ticket D2; `frontend/src/app/` and `state/` are Moon's, D-17). Area search uses the shell as [A21](../sky-shell.md) specifies it (layout, rail, surfaces, sky interaction, split pane, keys, hash) and changes nothing it already does for a searched object. Where A21 marks an extension point **To build (proposed, Q-170 to Q-177)**, Area search depends on it and names it; those placeholders are A21's, not this fragment's. Track's own screen is [A20](track-ui.md); this fragment only opens it.

Mock-up: `mockup/spherex-ui.html`, mock-up tool 5 (the app adds no number keys, Q-121). How to run it: CLAUDE.md "Layout". Visual input only (D-01).

## A18 Area search in the sky view

> **Note ([Q-414](../../decisions/shell-surfaces.md), PR #104, `feat/ui`):** the **Known objects** and **Discovery** flow built in this PR is a frontend demo, not A18. It is started from the sky dock (A21.4) and answers through `app/area/areaService.ts` only when the drawn area overlaps the prepared 433 Eros area (the box of `public/demo/eros/eros.json`); elsewhere it refuses with `area:not_prepared`. Its cards and the canvas carry a "Demo data" tag. It does not read `/v1/areas` (Q-205). Which of this demo and PR #100's real Area UI survives is open (Q-414).

**Principle: one sky.** Area search is one **tool** in the left rail, a **square** drawn on the sky, two **layers** (Dots, Tracks) and **feature cards** (A21.5). Target markers, cached markers, the picked position and click-to-pick keep working outside the drawing step.

### A18.1 Tool and drawing

> **Superseded in part.** The drawing steps below (a dragged square, pointer mode `draw`, Draw again) and the #144 aim-then-draw bullet describe earlier designs. What is built today is the last bullet (#157, Q-472): a click selects a region; the button that starts over is **Choose another region**. The draw step's code was removed in PR #166.

- **New tool** by the A21.13 checklist ([A21](../sky-shell.md)): `ToolId` in `frontend/src/app/shell/shellStore.ts` gains `'area'` (A21.4); `ToolRail.tsx` gains an **Area search** button with the hint "Draw a square, then follow known objects or look for movers"; its icon is a `SHAPES` entry in `shell/railIcons.tsx` (the compiler requires one per `ToolId`); `shell/icons.tsx` only if a card header needs it. Choosing another tool leaves Area search and keeps its state in the store, so choosing it again restores the square and the card.
- Choosing the tool opens the **Area** card ("Drag a square over the part of the sky you want to search") and switches the sky's pointer mode to `draw` (A21.6, Q-174): crosshair cursor; a drag draws the square instead of panning; the wheel still zooms. Buttons: **Use a square in the middle** and, when there is one, **Keep the last square**.
- The square is drawn in the accent colour (dashed while dragging, solid after) with its size in degrees above its top-left corner. A square under 30 CSS px on a side is refused with "Drag a bigger square".
- On release the frontend picks the prepared area holding the square from the `GET /v1/areas` index (A16.4). None: the card says "This part of the sky is not prepared" (`area:not_prepared`) and lists the prepared areas with **Fly there**, which uses `skyFlyTo` (A21.6, Q-174) and respects reduced motion.
- Releasing a valid square sets the pointer mode back to `pan`, so later clicks reach the layer hit-tests and the pick (A18.2); **Draw again** (A18.5) sets `draw` again.
- Escape leaves drawing mode and keeps the square, at rank 3 of the Escape order in A21.10 (Q-170). The pointer mode returns to `pan`.
- **As built, then superseded by #157 (issue #144, Q-462; live-areas mock-up states 1 to 6, 13 Nov 2026):** the dock's Known objects and Discovery start by **aiming** (`areaStore` stage `aiming`): the mouse pointer is a green rectangle with the screen's shape, drawn to scale (`app/area/aim.ts`, `app/sky/AimOverlay.tsx`), labelled "Next view · w° × 2.2°". A drag still turns the sky; a click (a tap on touch, where nothing is drawn before it) flies north up to a view 2.2° tall (the sky camera has no roll) and the stage becomes `drawing`, with a + pointer. The box follows the drag and stops at 2° a side (`clampDrag`); the readout over it says "2.00° × 1.06° · 2° max" while held, so no "too large" refusal reaches the user. Enter is the keyboard way: while aiming at a view more than twice as tall as the next one it zooms to the middle (as a click there), otherwise it sets a centred box of at most 2° a side. Escape leaves the tool. The hint sits at the top centre ("Click a patch to zoom in · drag to turn the sky", then "Drag to draw your area · up to 2° a side"). On release a prepared area goes to the existing flow unchanged (A18.5, Q-406); `area:not_prepared` runs the coverage check (`POST /v1/areas/live`, `start: false`) inside the same search and opens the **live card** (`app/area/LiveAreaCard.tsx`, `liveJobStore.ts`): the offer (data, visit pair, frames, time; Compute this area, Draw again), computing (six steps with check marks, a count and bar on the current one, elapsed and remaining; Minimise, Stop), waiting (Cancel) and failures (a status dot, a title and one muted line; Try again only where it can help). No icon tile in its header; Lucide `minus` and `x`. Minimise folds it into the island's pill ("Discovery · Step 2 of 6 · Download frames", A18.4; issue #146 #153: while minimised the pill also names the offer and a failure, "<flow> · Ready to compute" and "<flow> · Could not compute", `liveMiniTitle` in `liveJobStore.ts`). Closing the card does not stop the job; when it is done the area opens in the existing Known or Discovery views (the hand-off), unless another area's card is open. Stop and Cancel return to the offer (a job that ends `cancelled` does too). A job the server no longer knows (404 `job_not_found`), or 30 polls in a row without a reply, fails as "Frame archive not reachable". The request never asks for more than 2° a side. The job API is one module (`app/area/liveAreaApi.ts`) on #141's schemas (`area-live-plan`, `area-job`); a backend that does not serve the route keeps today's refusal, and the mock answers only when asked (`?live=mock…`), so no visit pair is ever made up. The results views themselves are #145.
- **As built (issue #157, [Q-472](../../decisions/moving-objects.md); live-areas mock-up states 1, 2, 10 and 11, 13 Nov 2026):** the aim and draw steps above are replaced by **selecting a region** (their code, the `drawing` stage, the drag clamp and its readout, was removed in PR #166). The pointer is the region, with the screen's shape, 35% of its height and drawn to scale; zooming the sky resizes it, up to 12° a side ("8.6° × 5.4° · 15 squares · about 11 h", `app/area/scanGrid.ts`, `app/sky/AimOverlay.tsx`). A click, tap or Enter flies north up so the region fills the screen. One square opens the single-area flow above. More squares: the whole screen is gridded (#156's split: equal squares whose padded boxes stay within 2°, numbered row by row from the top, `app/sky/ScanOverlay.tsx`) and the scan card (`app/area/ScanCard.tsx`, `scanStore.ts`) offers Start scan. It then follows the run (`GET /v1/runs/{id}`, #156; the running square's steps from its `progress`) square by square, circles each finished square's objects with their trajectories (`scanObjects.ts`; predicted ones hidden by default), and ends with the combined results (Found / Known, Track it, Build it, Export ECSV, Scan again). A reload mid-scan restores the run (its id is kept in localStorage). The API is one module, `app/area/scanApi.ts`, on #156's generated types; a mock answers only with `?scan=mock` on the dev server.
- **As built (issue #158, [Q-473](../../decisions/moving-objects.md); live-areas mock-up states 12 and 13, 14 Nov 2026):** a **runs button** right after the RA/Dec readout (`app/shell/RunsMenu.tsx`) lists every run of `GET /v1/runs` (#156), newest first, with an All / Discovery / Known filter; a row opens the run in #157's scan card (live progress, or the combined results), and its play button **replays** it: `app/area/replay.ts` gives the run as it was at time t (a pure function of the record), `runsStore.ts` keeps the deterministic clock (1×, 10×, 60×, 600×; one step a second under reduced motion), #157's `ScanOverlay` draws it watch only with "found at" labels on found objects (a predicted circle keeps its own line), and `app/sky/ReplayBar.tsx` draws the tag and the bar (play or pause, timeline slider with ticks, time, square count, speeds). Escape, the runs button or another tool ends it. Nothing is computed again.

### A18.2 Sky layers (`frontend/src/app/sky/area/AreaLayer.tsx`)

- **One 2D canvas** in the **sky layer slot** of A21.2 (after the edge fades, before the markers, cards and panel), `pointer-events: none`. Hits go through the layer hit-test chain of A21.6 (Q-174), run after marker buttons and before the sky's own pick; the A21.13 sky-layer checklist applies.
- **Drawn from the SkyPane render listener**, as the markers are: positions from `raDecToScreen` on every camera, visit or step change, written straight to the canvas with no React re-render. Device pixel ratio capped at 1.5 (D-05). RA wraps at 0/360.
- **Dots layer** (current visit only): before the stars step, star and fixed dots are white rings; after it, a faint cross. Glitches are rings in their wavelength colour until the glitch step, then hidden. Movers-to-be are rings in their wavelength colour (`wavelengthColor.ts`, tag `derived` as Rainbow Trails is built, Q-27 open). Dots with `OUTLIER` are drawn like the others (A16.5).
- **Tracks layer** (after the join step): each tracklet as a short line through its exposures with a dot per frame, and a dashed line joining the two visits. `found_blind` uses a short dash and the accent label; `unexplained` a long dash in amber; `unchecked` a dotted line in grey; `possible` has no join line. Colour is never the only cue (R9). The selected track gets the four-corner bracket used for the selected object.
- **Known positions** (Known card open): a small diamond per frame time at the Horizons position, joined by a thin line, tag `model_dependent`.
  - **As built (issue #130):** `app/area/KnownPositionsLayer.tsx`, an SVG over the sky (not the canvas of this section), repositioned from the view's render listener, drawn while the Known list is open, and on the Eros card only for an object with no demo sky image (otherwise the track window draws the path and the diamonds step aside, so one object never shows two paths); one diamond per distinct frame time (the two detectors of an exposure share one), the line split where a position is behind the camera. "Measured only" removes it (also every path on the Eros card's Track canvas, real or demo, and the cutout's Predicted position and Path overlays) and shows "Tracks and known paths are Estimated" (`knownPositionsVisible`). It replaces the demo path of `eros.json` pixels in the Known flow; the sky image under the track window is still the demo, used for 433 Eros only.
- **Honesty toggle (D-21):** "Measured only" keeps the dots (measured centroids placed through the frame WCS), drawn in one colour as Rainbow Trails does; it hides track lines, labels, verdicts and Known positions and shows the note "Tracks and known paths are Estimated". "+ Estimated" (the starting state) shows everything. Nothing in Area search is `artistic`.
- **Labels** at the last dot: "T1 · found blind = 433 Eros", "T2 · unexplained track", "T3 · possible · 1 visit", "T4 · not checked" (A16.5). Clamped inside the safe rectangle of A21.2 (insets, credit, open card; `skySafeRect()`, Q-174); hidden when the view is wider than 30°.
- **Picking.** With the Tracks layer on, a click within 20 CSS px of a track's dot opens its Result card (A18.7). A marker button wins over a track hit; a track dot under a marker is reached from the results list. Otherwise the click falls through to the sky's own pick or the marker's left click, which leave Area search for the object panel while the tool keeps its state (A21.13 item 4, Q-175). Right-click keeps its Q-120 meaning (the object card).
- **Text alternative:** a second id appended to the sky canvas's `aria-describedby`, never replacing the shell's instructions (A21.12): "Area 1.05° by 0.63°, visit 2 of 2: 4 movers, 1 found blind as 433 Eros, 1 unexplained, 1 not checked, 1 possible."

### A18.3 Visits and blink

- Discovery shows one **visit** at a time, chosen in the Discovery card with a segmented control "Visit 1 · date, time UTC | Visit 2 · …". The transport belongs to the flipbook, has no modes and is not used (A21.9, Q-175).
- **Blink the 2 visits** is a toggle button (`aria-pressed`) in the same card. While pressed it switches visits every 750 ms (under 3 Hz), the classic way to spot a mover by eye: stars stay put, movers jump. It stops when pressed again, when the Discovery card closes, when the Track pane opens and when the tool changes (WCAG 2.2.2). Under reduced motion it is off by default and each press steps one visit.

### A18.4 Cards and minimise

- **Surface.** Every Area card is a **feature card** of A21.5 (Q-172): it renders in the object card's slot (top centre, 340 px, z 25), shown only while `tool` is `area`, so it never meets the object card. A wider card needs a width token decided with it; the mock-up's 408 px is not used. Area cards never use the object panel.
- **Header:** title, **Minimise** and ×. × ends the current card and returns to the previous Area card, or to the sky from the Area card; focus goes to the Area rail button (A21.5).
- **Minimise** (Q-146 item 3; mechanism A21.5, Q-172, amending Q-121 item 2): the card hides and the island takes its `progress` mode, a pill that is a button named "Show <card title>" and keeps showing progress ("Discovery · Step 3 of 5 · Drop stars", then "4 movers · 1 is 433 Eros"). **As built (issue #146, #153):** a minimised live card (the offer or a failed job, A18.1) reads "<flow> · Ready to compute" for the offer and "<flow> · Could not compute" for a failed job (`liveMiniTitle` in `app/area/liveJobStore.ts`); <flow> is Known objects or Discovery. So the whole square stays visible while the steps play. A click, Enter or Space restores the card as it is now and focuses its heading. The progress text changes no more than once per step.
- Right-click keeps its Q-120 meaning (the object card for a marker); it never restores an Area card.
- While the Track pane is open the Area card is hidden; **Back to the area** brings it back (A18.8).
- Cards: Area (A18.1), Options (A18.5), Known (A18.5), Discovery (A18.6), Result (A18.7).

### A18.5 Options and Known objects

- **Options card:** title "Area · w° × h°", subtitle "n SPHEREx frames in v visits · dates". Two large buttons: **Known objects** ("Follow asteroids and comets already on file that crossed this square") and **Discovery** ("Look for dots that move and match nothing on file"). **Draw again** under them.
- **Known card:** one row per object from `/known` (A17.8): number and name, kind, frames and visits, and an action:
  - **Track it** when `track_available`: opens the Track pane for `object_id` ([A20.1](track-ui.md#a201-where-track-lives)).
  - **Open** otherwise: searches the object as a left click on its marker does (Q-120), so the object panel opens and Area search is left while the tool keeps its state (A21.13 item 4, Q-175). The row says why Track is missing ("Track not prepared for this object offline").
- Each row has its provenance badge (Estimated: SkyBoT and Horizons, A16.5) and the date of the SkyBoT answer.
- **As built (issues #96 and #130, [Q-406](../../decisions/moving-objects.md), [Q-455](../../decisions/shell-surfaces.md)):** `app/area/areaService.ts` `knownObjectsIn()` snaps the square to a prepared area of `GET /v1/areas` (`findArea`, `sky/area/snap.ts`) and reads its `/known` (`loadKnown`); `knownRow` maps each object, and `KnownList.tsx` draws the rows: `track_available` rows say **Track it** and open the Eros card (the demo object `sbdb-20000433` is always Track it: the committed pack still answers `track_available: false` for it until backend #129 lands, and the card falls back to the demo for Eros); the rest say **Open** (`skySearch`, as a marker click) with "Track not prepared for this object offline". The card's foot (`RealAreaNotes`) says when the area ran, "Test data" for a synthetic area, and lists `missing` codes in plain words (`missingText`); one line gives the latest SkyBoT answer of the area's visits (SkyBoT answers per visit, not per object). No prepared area, or an index that cannot be read (no backend, or a failed or invalid reply): the demo row over Eros, `area:not_prepared` elsewhere; a prepared area whose `/known` fails or breaks the contract: `area:failed`. One `AbortController` per square. The dev fixture server answers the same routes with synthetic areas (at RA 150 and RA 210), so a square over Eros finds no prepared area there and gets the demo Eros row. Discovery: prepared area (Q-406), else the demo.

- **As built (issue #145, [Q-466](../../decisions/moving-objects.md), [Q-469](../../decisions/moving-objects.md); live-areas mock-up states 6 to 9, 13 Nov 2026):** `loadKnown` reads the area's summary and `/tracks` beside `/known` (and `/dots` only when a track matched a known object). `KnownList.tsx` shows the provenance lines (`RealAreaNotes`: "Computed live" for a `live-…` area, else "Precomputed", with the run time and release; the two visits and the frames; when SkyBoT last answered), the All / Detected / Predicted filter, rows sorted detected first then by V, 40 rows then "Show all", each row with Track it and Build it (Lucide `route`, `box`). Track it opens the Eros card when `track_available`, else starts a Track on demand (`app/area/trackJobApi.ts`, `trackJobStore.ts`, `TrackJobCard.tsx`; #142's `POST /v1/objects/{id}/track` then `GET …/job?around&days`, the job of that window, and the Track view reads `/frames` and `/path` with the same window ([Q-478](../../decisions/moving-objects.md) (2)); mocked only with `?track=mock` on the dev server). Build it searches the name and opens the build view (`app/area/buildFrom.ts`). A refusal is a status dot, a title and one line with Draw again ("No data for this area here · This server cannot compute new areas…", held issue 6). The "Open" row and its "Track not prepared offline" note are gone. The offer card has a visit pair picker when the plan lists `alternatives` (#141's optional `visits`; another pair is another area).

### A18.6 Discovery card

- **Note** (amber while fixtures are in use; in the event build replaced by `computed_at`): what is demo and what is real.
- **Five steps**, each a row with a check, a name and its count from `steps` (A17.8): Find dots · Drop one-exposure glitches · Drop stars and fixed dots (Gaia DR3, CatWISE) · Join what moves across visits · Check known objects (SkyBoT, Horizons). **Look for movers** replays them one second apart (at once under reduced motion), turns both layers on and fits the camera so the square sits in the safe rectangle below the card (A21.2; `skyFlyTo`, A21.6, Q-174). Afterwards the button reads **Run again**. The blink stays off until the user presses it (A18.3).
- **Results list:** one row per track or possible, rendered from the start (greyed "waiting") so the card does not change height: id, "Moves across both visits" or "Seen in 1 visit", frames, and a chip: `433 Eros` (green), `unexplained` (amber), `not checked` (grey) or `possible`. A row is a button that opens the Result card.
- The reveal is announced through the shell's `announce(text)` action (A21.12, Q-176; today `LiveAnnouncer` reads only `sky.announcement`): "4 movers: 1 is 433 Eros, found blind; 1 unexplained; 1 not checked; 1 seen in one visit".
- **Checks** (gated extras, Q-203): below the results list, a **Checks** section (A18.11) appears when the area has a `checks` entry; otherwise nothing is shown.

- **As built (issue #145):** the Discovery card shows the same provenance lines, and once the steps are done "Detection rates not measured yet · Treat possible tracks as leads." (until the checks D4 to D7 exist), Export ECSV (`/v1/areas/{id}/export.ecsv`) and Draw again. Track labels on the sky never overlap (`placeLabels` in `sky/area/drawLayer.ts`: four spots per label, ranked selected, found blind, unexplained, the rest; a label that fits nowhere is not drawn). A track's card (`RealTrackCard.tsx`) gives visits and dots, rate and direction, the match ("433 Eros · 0.31 px from predicted"; `matchName` no longer doubles the number, held issue 1), its tags, and Track it, Build it and Back (Q-469).

### A18.7 Result card

The card for one Discovery result (called "Track card" before; renamed so "Track" on screen means only the Track tool, **Proposed (Q-182)**). The result itself is a "Discovery track" in the docs; its on-screen labels stay as Q-146 wrote them.

- Header: the id; subtitle "Matches a known object", "Matches nothing known", "Not checked" or "Seen in one visit". Chips: `Known: <designation>`, `Unexplained track`, `Not checked` or `Possible · one visit`, plus the dev-only Fixture badge.
- One sentence per verdict:
  - found blind: "The search was not given Eros's position. We chose this area because Eros crossed it; the known-object check then named it 433 Eros."
  - unexplained: "Moves steadily across both visits and matches nothing known to SkyBoT as of <date>. A lead for follow-up, not a discovery."
  - unchecked: "Moves across both visits. It could not be checked against known objects (<reason>)."
  - possible: "Moves within one visit only. It needs a second visit before it counts as a track."
- Facts with badges: visits, frames, glitch check, star check, known object and separation (Estimated), apparent rate and direction between visits, labelled "apparent, seen from SPHEREx" (`derived`; the rate inside a visit is not shown, Q-134), and the dots with flags (`OUTLIER` named, Measured).
- **Spectrum check (A17.13, Q-474, proposed; spectrum-check mock-up linked from Q-474):** data from `GET /v1/areas/{area_id}/spectra`, read with `/tracks`. Results rows end in a status dot and one word: Rock-like (`--ok`), Very red and Too red (`--warn`), Too blue and Flickers (`--fail`), Too faint and One colour (muted). The results filter gains "Rock-like n". Under "Measured only" the chart shows only the points, and the verdict, range and heat-glow line are hidden. 404 `spectra_not_prepared` adds "Spectrum check not run" to Not shown. The verdict never changes the track's own verdict sentence or its order.
  - **As built (issue #162, [Q-474](../../decisions/moving-objects.md), [Q-476](../../decisions/moving-objects.md); spectrum-check mock-up states A to F, 14 Nov 2026):** `app/area/spectraApi.ts` is the one client (`areaSpectra(areaId, signal)`, generated `AreaSpectra` types, a reply check): `ok`, `not_run` for 404 `spectra_not_prepared` (`spectra:not_run`, "Spectrum check not run" under Not shown) or `unavailable` for anything else (`spectra:unavailable`); `realArea.loadDiscovery` reads it beside `/tracks` and it never fails the area. No mock: the committed Eros pack holds the real stage. The chart draws dots with `used` and `point` both true and a non-null `rel` (a dot below `snr_min` enters only as a limit arrow); the Spectrum section's tag is the D-02 badge of the reply's `provenance.colour.tag` (Estimated on Eros), and of `provenance.points.tag` under Measured only. ### A18.8 Hand-off to Track

- **Open in Track** and **Track it** call `openPane({ kind: 'track', objectId, from: { area: areaId, card } })` (A21.8, Q-171), never `setTool`, so the tool stays `area`. The pane is the only occupant: Track replaces Build in place and the reverse. Its width is the shell's per-kind `--sx-split-w` (A21.8; Track's value is proposed in [A20.1](track-ui.md#a201-where-track-lives)).

- The pane header has **Back to the area**: it closes Track, reopens the card the user came from and focuses its heading (A21.8 focus return for `from: area`). × and Escape close it too; Escape closes the pane before anything else of Area search (A21.10, Q-170).

### A18.9 State, API client, accessibility, performance

- An `area` slice in `frontend/src/state/store.ts`: `index`, `areaId`, `square`, `summary`, `known`, `dots`, `tracks` (each `idle | loading | ready | error`), `layers {dots, tracks}`, `step`, `visit`, `blink`, `selectedResult`, `card`, `minimised`.

- **URL hash** (A21.11, Q-173): `area=<area_id>` (sets the tool to `area` and opens that area's card; an unknown area is a link problem), plus `atrack=<T-id>` for an open Result card (`track=` belongs to the Track pane). A hash with only tool keys is valid. A new area pushes; choosing a result or a step replaces.
- Copy in `app/messages.ts`; refusals through `refusals.ts` and `RefusalList.tsx`.
- **Keys (A21.10):** no number keys (Q-121). The square is its own focusable element (`role="group"`, label "Search square, w by h degrees"); while it has focus, the arrow keys move it and Shift + arrows resize it, with `preventDefault`. On the sky canvas the arrows still pan (Q-123).

- **Sound:** Track owns the sound for a known object (Q-134). Discovery adds none for the event build. Desktop only (Q-132).

### A18.11 Checks

**Gated extras (Q-203), proposed.** Built only if its ticket passes the gate of [A16.7](area-plan.md#a167-tickets-and-plan); until then the Discovery card has no Checks section and nothing is greyed out or promised. Not in the mock-up yet. Data: `GET /v1/areas/{area_id}/checks` ([A17.8](area-contract.md#a178-endpoints)).

Payload: a part is present only when its ticket ran; `checks:d4_not_run`, `checks:d5_not_run` and `checks:not_run` in `missing` say which did not ([Q-208](../../decisions/moving-objects.md) (12)).

- **Where.** A **Checks** disclosure at the foot of the Discovery card, closed until Discovery has run. Each part appears only if its data exists; a part that is missing says so ("Control not run") and its code goes to the refusal list, never an empty frame.
- **Planted test mover (D4).** A switch **Include a planted test mover**, off by default, enabled after the first run. On: the planted path is drawn on the sky with a dashed outline and the label "Injected", and one row "Test · planted by us · recovered" (or "not recovered") joins the results under a divider headed "Planted, not real". The row opens a small card: "We planted this mover. The search was not told where, and it found it." (or "did not find it"). It is excluded from every count, from Known and from the export. Badge **Injected**: text plus an outline colour that is not the green, amber or grey of the real verdicts, so colour is never the only cue (R9).
- **Completeness grid (D4).** A table, rows = rate bins (deg/day), columns = S/N bins. Each cell reads "k of n" and is shaded by the fraction, with its interval in the tooltip. Row and column headers are real table headers. Fixed caption: "How often the search found movers we planted in this square. It is not a catch rate for the real sky." Badge Estimated. No single summary number appears here, in an announcement or in the export.
- **Control line (D5).** "Scrambled-time control: n false tracks in m runs" (Estimated); the seeds are in the details.
- **Linked by (D7)** is part of the Result card (A18.7). The spectrum check is not a gated extra (A18.7, Q-474).
- **Announce.** Through `announce(text)` (A21.12, Q-176): "Checks: test mover recovered; 0 false tracks in 20 scrambled runs."
